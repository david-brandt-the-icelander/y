# Runtime generations

> Status marks: [knowledge-driven development](https://github.com/david-brandt-the-icelander/knowledge-driven-development)

**Written for:** whoever implements the runtime, and whoever operates a Y system in production.

## What it is

Everything else in this corpus describes a language. This describes a running system in which the logical
program, its physical representation, and its state each have their own version, and any of the three can
be replaced while the system runs.

The thread connecting the parts is that **a proposal does not have to be trusted if it can be checked
against a real workload.** Given deterministic semantics, a captured workload and a way to compare two
executions, a candidate implementation can be arbitrarily speculative — generated by a search, by an
agent, by a genetic algorithm — because promotion is gated by mechanical verification rather than by
review. A bad candidate is slow, not wrong.

## Deterministic replay

Everything downstream depends on this, and nothing downstream is sound without it.

- ⚠️ An execution's non-deterministic inputs are captured: the clock, randomness, external query results,
  durable command outcomes, and the transaction commit order that produced the observed snapshots.
- ⚠️ A captured execution replays to an identical result — identical observable output, identical committed
  state, identical emitted commands — on a different machine and at a later time.
- ⚠️ Replay is cheap enough to run over a corpus of production executions rather than a handful of saved
  cases.
- ⚠️ Two executions are compared mechanically on what Y considers observable: results, failures, external
  effects emitted, state transitions taken, and serialised committed state.
- ⚠️ Determinism holds from Core IR down. A physical decision — a layout, an index, a schedule — must not be
  observable to a Y program, and one that is observable is a bug in the runtime rather than a caveat on
  replay → [core-ir.md](core-ir.md).
- ⚠️ Production emits a telemetry stream per invocation: the function's logical identity, its code version,
  an input fingerprint, the state version observed, effects consumed, and cost — execution time,
  allocations, reads, writes, cache misses, transaction retries.
- ⚠️ The telemetry stream is eventually consistent and the consumer may be hours behind. Nothing in the
  latency path waits for an optimiser.

## Two optimisers

- ⚠️ **The semantic optimiser must be correct.** It proves and transforms: purity, whether a transaction may
  retry, whether a reference escapes, whether two operations commute. It lives in the compiler
  → [compiler-pipeline.md](compiler-pipeline.md), and a wrong answer from it is a wrong program.
- ⚠️ **The physical optimiser may be experimental.** It chooses representation and execution strategy, and a
  wrong answer from it is a slow program. This is what licenses stochastic search: the two are separated so
  that the part that may guess cannot change meaning.
- ⚠️ The physical search space is a set of discrete parameters attached to Core IR rather than choices baked
  into generated code: relation layout (row, column, hybrid); index (none, hash, B-tree, radix); versioning
  strategy (row MVCC, page MVCC, epoch, double buffer); entity storage (sparse set, archetype, chunk size);
  graph representation (adjacency list, CSR, indexed edges); vector layout (AoS, SoA, AoSoA with a width);
  alignment; partitioning and co-location; and caching, materialisation and eviction.
- ⚠️ A candidate is a complete assignment of those parameters, and candidates are generated by any means —
  enumeration, hill climbing, annealing, Bayesian optimisation, a genetic algorithm crossing two parents, or
  an agent proposing one.
- ⚠️ Fitness is multi-objective — latency at a percentile, throughput, memory, commit-conflict rate, network
  traffic, startup time — and semantic equivalence is a constraint rather than an objective. A candidate that
  fails equivalence is discarded regardless of its score.
- ⚠️ The optimiser proposes code transformations as well as parameters: fusing loops, materialising a query,
  hoisting a computation out of a transaction, batching lookups, splitting or merging transactions,
  prefetching, vectorising, caching a pure computation. Each is validated by replay rather than by
  argument.
- ⚠️ Physical optimisation is profile-guided at the level of the data model, not just the code — the
  telemetry shows which access paths dominate, and the optimiser restructures storage around them,
  including deciding that two relations should live together.
- ⚠️ A program may override a physical decision, and an override is explicit, visible and rare — a program
  full of overrides is a program whose optimiser is not trusted, which is a finding rather than a style.
- ⚠️ A winning candidate is an artefact a human can inspect, review and reject, not a silent change.

## Versioned code and hot swap

- ⚠️ Every function has a stable logical identity independent of its implementation, and every call is a
  dispatch through a version slot rather than a fixed address.
- ⚠️ Several versions of a function coexist, and the active one is selected by metadata.
- ⚠️ Substitutability is decided by the compatibility signature — parameters, return representation, effect
  set, transactional writes, durable command classes, contracts → [core-ir.md § The compatibility signature](core-ir.md#the-compatibility-signature).
  A candidate whose signature differs is not a transparent swap, and the runtime refuses it rather than
  permitting it with a warning.
- ⚠️ A candidate runs in shadow first: both versions execute against the same snapshot and the same captured
  effects, only the active version's result is externally visible, and the two are compared on results,
  writes and emitted effects.
- ⚠️ A candidate that survives shadow is canaried on a fraction of invocations, and its telemetry is compared
  against the active version's on the same workload.
- ⚠️ Promotion and rollback are atomic metadata operations. Rolling back is selecting the previous version,
  and costs no deployment.
- ⚠️ An in-flight invocation is never swapped underneath itself: a call that started on one version finishes
  on it, and a new call starts on the newly active one.
- ⚠️ A version is unloaded when no invocation of it remains, by epoch-based reclamation rather than by a
  timer.
- ⚠️ A suspended workflow persists its logical function identity and a semantic continuation version rather
  than any address, and resumes under either the latest compatible implementation or the one it suspended
  on, according to a declared migration rule
  → [`../language/external-effects.md`](../language/external-effects.md).
- ⚠️ A defect is fixed by the same mechanism as an optimisation: replay the failing production case against
  the candidate, confirm it produces the correct result where the active version does not, shadow it against
  recent executions, promote it. There is no separate patch path.

## The promotion gate

- ⚠️ No candidate reaches production except through this sequence, and each step can reject: compile; verify
  contracts and invariants; replay the captured corpus; compare observables; shadow against live production;
  compare again; canary; promote.
- ⚠️ **The optimiser may propose anything; promotion is mechanically gated.** An agent or a search may
  replace an algorithm, change a layout, fuse loops, specialise constants, move computation, introduce
  vectorisation or change indexing. None of that is privileged, because none of it is trusted.
- ⚠️ A gate is never skipped for urgency. An urgent fix is a candidate with a small corpus, not a candidate
  with fewer gates.

## Live state migration

- ⚠️ Persistent state is migrated to a new representation while the program continues to use it, and the
  visible pause at cutover is proportional to the remaining difference rather than to the size of the state.
  This is the mechanism behind `converge`
  → [`../language/data-and-schemas.md` § converge](../language/data-and-schemas.md#converge).
- ⚠️ The migrator snapshots the source at a version, transforms into the target, and records the source
  version each migrated fragment was derived from.
- ⚠️ **A conflict retries a fragment, not the migration.** A source record that changed after its fragment
  was migrated makes that fragment stale; every other fragment stays valid. The migration converges instead
  of restarting.
- ⚠️ Staleness is computed from recorded read sets: a fragment that read a customer at one version and a
  country rule at another is stale when either of those changes and not when some unrelated record does.
- ⚠️ Staleness propagates along declared references — a changed customer invalidates the orders referencing
  it and the invoices derived from those orders — and no further. This is what declared references buy that
  arbitrary pointers do not.
- ⚠️ The migrator reports the size of the stale set over time, so a migration that is not converging is
  visible before a cutover window is chosen.
- ⚠️ Cutover uses a version fence rather than a write pause where the transaction semantics allow it: the
  target is guaranteed to represent the source exactly through a chosen version, transactions starting after
  that version use the target, transactions already running finish against the source, and the source is
  retired once none remain. Where a fence is not available, a write barrier is held for the final
  difference only.
- ⚠️ Both representations may be kept live after cutover, with commits replicated to the retired one, so that
  a problem discovered later is resolved by switching back rather than by migrating again.
- ⚠️ A migration may be perpetual: hot records migrate eagerly, cold records on access, reads understand both
  representations, and support for the old one is removed when no record remains in it.
- ⚠️ The same mechanism performs a physical representation change with no logical schema change (one vector
  layout to another, B-tree to hash, row-store to columnar, adjacency list to CSR, heap-backed to
  memory-mapped), a repartitioning, and a relocation of state between machines — a relocation is a
  convergent copy followed by an ownership handoff.
- ⚠️ Migration functions are constrained so that partial retry is safe: deterministic, pure with respect to
  external systems, idempotent, dependent only on versioned state, and replayable. The language enforces
  this → [`../language/data-and-schemas.md` § Migrations](../language/data-and-schemas.md#migrations).

## Generations

- ⚠️ A generation is a named tuple of everything that must change together: a code set, a logical schema
  version, a physical plan, and a shared-state root.
- ⚠️ A new generation is constructed alongside the active one — its state converged, its code shadowed — and
  activated by one atomic metadata operation.
- ⚠️ A deployment is an activation of a generation rather than a replacement of binaries, and a rollback is
  an activation of the previous one.
- ⚠️ A retired generation remains available for draining, rollback, replay and comparison, and is discarded
  on a stated policy rather than immediately.
- ⚠️ A code change that requires a schema change is one generation, so there is no window in which new code
  runs against old state.

## What v1 must not foreclose

Whatever is decided about the ambition, these are the primitives the transcript identifies as cheap now and
a runtime redesign later. They are listed here so the decision is about a list rather than a vibe.

| Primitive | Status |
| --- | --- |
| Stable logical identity for every function, independent of its implementation | ⚠️ |
| An explicit code-version identity on every invocation | ⚠️ |
| Deterministic, replayable capture of non-deterministic inputs | ⚠️ |
| Versioned shared-state schemas | ⚠️ |
| A dispatch indirection cheap enough to select an implementation per call | ⚠️ |
| Retention of several code versions simultaneously | ⚠️ |
| Telemetry describing execution cost and shared-state access | ⚠️ |
| Shadow execution against a snapshot and captured effects | ⚠️ |
| Mechanical comparison of results and write sets | ⚠️ |
| Atomic promotion and rollback of a function version | ⚠️ |

## Failure modes

| Symptom | Cause | What it looks like from outside | Handled? |
| --- | --- | --- | --- |
| Replay diverges from the captured execution | A non-deterministic input not captured | Every gate downstream becomes unsound while continuing to report success | ⚠️ |
| A promoted candidate changes behaviour | Comparison did not cover an observable, or the corpus missed the case | A production incident from a change that passed every gate | ⚠️ |
| A hot swap is accepted across a semantic change | Compatibility signature under-specified → [core-ir.md](core-ir.md) | An external effect appearing in a function that had none | ⚠️ |
| A physical decision becomes observable | Ordering, timing or capacity leaking through an abstraction | A program that depends on a layout, breaking when the optimiser changes it | ⚠️ |
| A migration never converges | Source churns faster than fragments migrate | A migration that runs forever with no cutover window | ⚠️ |
| Cutover stalls | A long-running transaction on the source never drains | A fence that cannot close, holding two representations live | ⚠️ |
| The optimiser overfits | Corpus unrepresentative of live traffic | Candidates that win on replay and lose in production | ⚠️ |
| Generations accumulate | Retention policy absent or never applied | Storage consumed by generations nobody will roll back to | ⚠️ |
