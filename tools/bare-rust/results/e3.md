# E3: edits

Proposal § 10: over each corpus's history, strip the older version of a changed file, take the newer bare body, and weave it with the older constraint file; count the slots that no longer bind and the holes that become undetermined. Slots attach to named items and parameters, so most body edits should leave them untouched; this measures how true that is.

**Method.** `bare-rust e3 <repo>` walks `git rev-list --reverse --no-merges <range>`. For each commit it takes the first parent and every `.rs` file the commit *modifies* (added and deleted files are counted but not compared; renames appear as delete plus add) that belongs to the crate at the new commit (`corpus_files`: library, binaries, tests, and the modules they declare). Per file it strips the parent's version (`bare_old`, `json_old`) and the new version (`bare_new`, `json_new`) and classifies the change by comparing the canonical JSON:

- *identical*: `bare_old == bare_new` and `json_old == json_new` (the edit was erased by the strip);
- *body-only*: `json_old == json_new`;
- *body-only, holes changed*: the two files differ in `holes` (the `locals` and `hints` entries that belong to bodies) and nowhere else;
- *signature-changing*: anything else.

It then weaves `bare_new` with `json_old` (no cargo) and records the entries of `json_old` that bind to nothing (`unbound local`, `unbound hint`, `unbound subject`), whether the woven file equals the new original after `normalise_nomut` and `rustfmt`, and, if not, whether it differs only where a slot is woven in (`strip` of the woven file gives back `bare_new`). A weave that is refused (a new item has no entry, a parameter count changed) is counted by reason.

For each commit with a file that is signature-changing or has changed holes, and that wove, the files are put into a copy of the new commit (`git archive`; the pinned checkout under `corpora/src` is only read with `git`) and `cargo check --all-targets` runs. First the new commit as it is: if it does not build, the commit is recorded as "baseline does not build" and goes no further. Then three weaves: **A**, `bare_new` with `json_old` as it is; **A'**, the same with every `locals` and `hints` entry dropped, as in check 4; **B'**, `bare_new` with `json_new`, holes dropped (the baseline of A'). *Compile failures attributable to the weave* are the errors and undetermined holes of A (the baseline builds, so all of them are); *new undetermined holes* and *new compile errors* are those of A' that B' does not have. `mut` is derived through rustc in all three.

**Reproduce.** From `tools/bare-rust`, after `corpora/fetch.sh` and `cargo build`. A shared target directory keeps cargo fast; each repository takes a few minutes.

```
export BARE_RUST_TARGET=$PWD/target/bare-rust-e3-cargo
bare-rust e3 corpora/src/strsim --work target/bare-rust-e3
bare-rust e3 corpora/src/fnv --work target/bare-rust-e3
bare-rust e3 --render target/bare-rust-e3/e3-strsim.json target/bare-rust-e3/e3-fnv.json
```

## Reading

- **About three changes in five do not touch a constraint.** Of 76 modified files in the crates, 39 are body-only (the constraint file is byte for byte the same), 5 more change only `holes`, and 32 change something in the signature (42 percent). Each of the 39 body-only files weaves back to exactly the new original after `rustfmt` (0 exceptions), with 0 unbound entries, which is the hypothesis of § 10 for the cases where it can be tested without a compiler. Commits that touch a `.rs` file are 67 of 158; the others change docs, manifests and tests data.
- **Most signature changes add an item.** 23 of the 32 signature-changing files are refused by the weave because the new bare body names an item that the old file has no entry for (`slot missing: no subject ...`). That is the intended behaviour of "the weaver does no inference" (§ 2.3): an agent that adds a function must add its entry. It also means that what an agent edits in the JSON for a typical signature change is a new entry, not a change to an existing one. The other 9 weave: they remove or rename items or change types, and the files that weave leave 31 `unbound subject` entries (items the commit deleted: the `*_against_vec` functions, their tests, the benches), 5 `unbound local` entries (locals of removed or rewritten functions) and 2 `unbound hint` entries. Unbound entries are reported as warnings and do not stop the weave; none of them appears in a body-only file.
- **Holes bind by name and ordinal, and that is the fragile part.** The 5 files whose only JSON change is in `holes` are body edits that add or remove a `let` or a `cast`; fnv commit `c7a0509e` (a signature change) and strsim commit `f9eea82a` each leave one `unbound hint` (the n-th literal or cast of the function moved). With the old file kept, 2 of the 13 commits sent to cargo (both in strsim, `6ca79b06` and `5b512dce`) fail to compile because a new local has no entry: both are reported as "hole undetermined", with the clause that would fill it, and neither as a wrong-type error. The other 11 compile with the old file as it is. With the holes dropped on both sides (A' against B'), no commit gains an undetermined hole or an error: the signatures carry the weight, and what the old file adds to inference is exactly the entries for the locals and hints, which are kept up by the one who edits the body.
- **No silent damage.** Across the 13 commits cargo ran on, there is no E0308 or other type error that the old constraint file caused in a body; the baseline built every time (the old commits of both crates build on today's toolchain, with `RUSTC_BOOTSTRAP=1` for strsim's benches, as the other checks do). The woven file differs from the new original only where slots are woven in (0 files "differ elsewhere"), which is what the round trip guarantees.
- **A tool finding.** The first run showed that `weave` accepted a type alias with no entry in the constraint file and printed `type Foo;` without a type; rustc then failed with "free type alias without body". Weave now refuses it like any other item (`slot missing: no subject`), which moved those files from "compile failures" to "refused".
- **Limits.** The numbers are for two small crates, 76 changed files; the unit is the file, so a commit with several files is counted once per file in the first block and once per commit in the cargo block. Files refused by `strip` would be counted by reason in the second table; there are none, because the stage 1 productions cover both crates' whole histories. Added files (strsim: 3, fnv: 0) and deleted files (strsim: 0, fnv: 1) are not compared. `e3` weaves the new body with the *immediately previous* constraint file; a longer gap (several commits between the file and the body) would have more drift, and E4 is where that is tried with an agent writing the edit.
